# Task 2–5：代码做了什么，怎样向老师说明

这份说明用于理解实现和准备汇报。实际操作命令继续使用《我自己的实验重做记录》；这里不新增实验命令，也不把未做过的实验写成结果。

## 先说明整个系统的目标

合法业务是 h1→h6。当 h2 或 h5 突然产生高率流量时，控制器要识别并封锁异常源，同时根据网络状态决定合法 h1→h6 是否换路；最后用真实接收数据评价处理效果。

四个任务是连续的：**Task 2 识别并封锁异常源 → Task 3 把流量和异常状态转成链路代价 → Task 4 按代价更新合法流的转发路线 → Task 5 测量和解释实际效果。**

| 老师的任务 | 我们要回答的问题 | 主要代码 | 输出/验证证据 |
|---|---|---|---|
| Task 2 监测、EMA 检测、源封锁 | 谁的发包速率异常？怎样让它的包不再转发？ | `traffic_stats.py`、`anomaly_controller.py` | STATS、BLOCK、priority 5000 drop 及命中计数、h2 不通而 h1 仍通 |
| Task 3 动态链路代价 | 哪条链路现在较繁忙或受异常影响，选路时应降低其优先程度？ | `link_costs.py`、`dynamic_cost_controller.py` | 各有向链路的速率、利用率、负载项、惩罚项和恢复记录 |
| Task 4 合法流量改道 | 有更便宜的替代路时，怎样让正在通信的 h1→h6 真正走过去并恢复？ | `rerouting_controller.py` | ROUTE、实际流表/端口/计数、连续 ping、接收吞吐与丢包 |
| Task 5 性能评价 | 上述机制在异常前、中、后表现如何？ | `analyze_task5.py`、`compare_task5_b.py` | 三类时间曲线、A/B/C 比较、B 三轮结果及分析 |

`student_task4_experiment.py` 和 `verify_rerouting.py` 是实验安排与取证程序，负责启动流量、保存数据和检查结果；异常判断、封锁及改道由控制器完成。

### 三个启动版本是什么关系

`AnomalyController` 继承正常基线；`DynamicCostController` 在其上增加链路代价；`ReroutingController` 再增加改道。最终 Task 4 控制器包含 Task 2、3 的功能。

因此每轮只运行一个控制器。先分别验证检测、代价，再运行集成改道版本，是为了知道每一步是否正确；不是同时开三个 Ryu。Task 5 的分析程序读取日志，不再下发网络规则。

## Task 2：识别异常源，并把它的包挡在交换机上

**老师要求：**用 ping 模拟正常流量，维护 EMA 基线；用 hping3 产生高率 ICMP；超阈值后安装源 IP 防火墙规则，并验证异常流不再转发。

### 代码的输入、处理与输出

1. `anomaly_controller.py` 的 `stats_monitor()` 约每秒通过 OpenFlow 发送流表统计请求。交换机返回累计包数和字节数。控制连接是交换机到 Ryu 的 TCP `127.0.0.1:6653`，协议为 OpenFlow 1.3。
2. `traffic_stats.py` 的 `FlowRates.sample()` 用两次计数的增量除以实际时间间隔，得到包速率。每个源只在接入交换机统计，避免一个包经过三台交换机就被重复算三次；ICMP 回显回复不作为受害主机的新攻击请求计数。
3. `SourceEMA.observe()` 维护每个源的正常水平。至少五个有效样本预热后，先把当前速率与旧 EMA 对应阈值比较，再更新正常基线：

$$
r_t=\frac{\Delta N}{\Delta t},\qquad
T_t=\max(2000,3E_{t-1}),\qquad
E_t=0.3r_t+0.7E_{t-1}.
$$

只有未被封锁的样本更新 EMA；触发异常的样本不抬高正常基线。2000 pps 下限是我们的配置，用来避免基线接近零时把正常启动的 10 Mbps UDP 流误封；它不是老师强制指定的值。

4. `anomaly_controller.py` 的 `flow_stats()` 得到 `newly_blocked` 后，对每台交换机调用 `drop(dp, ip)`。该函数生成 `OFPFlowMod`：匹配 IPv4 与异常源 IP，优先级 5000，动作为丢弃。Ryu 经 TCP 控制连接发送消息，交换机解析后在流表中安装规则。
5. 后续数据包由交换机直接执行这条规则。普通业务包不需要全部绕到控制器；控制器主要通过统计获得速率，通过控制消息改变交换机行为。

### 为什么 h2→h6 被阻断，而 h1→h6 仍通

h2 发往 h6 的请求带有源 `10.0.0.2`、目的 `10.0.0.6`，经 h2-eth0 进入 s2-eth1。正常时匹配 priority 110 的 ICMP 转发规则，从 s2-eth6 发给 s6，再到 h6。

新增源封锁 priority 5000 后，该包同时匹配转发与封锁规则，5000 优先，因此在 s2 丢弃，h6 收不到请求，也就不返回对应回复。h1 的源 IP 是 `10.0.0.1`，不匹配这条 drop，继续正常转发。

**封锁的是 h2 发出的 IPv4 流量，目的地址不限；没有关闭 s2–s6 链路，也没有封锁 h6。** 规则安装前已有部分包通过是可能的，不能宣称所有异常包从一开始就被阻断。

**验证：**原 Task 2 观测到检测速率 13,339.8 pps、阈值 2000 pps；s2 drop 命中 478,615 包；之后 h2 ping 为 0/3，h1 为 3/3。完整后台合法 ping 为 292/293，不把这轮描述成零丢包。发包程序的 8 秒 timeout 只结束测试，不能代替封锁验证。

**汇报时可说：**“Task 2 的代码把交换机累计计数转换为源速率，用旧 EMA 判断异常，再通过 OpenFlow 下发高优先级源 IP 丢弃规则。我们用入口丢弃计数和两组 ping，确认异常源被阻断且合法源仍能通信。”

## Task 3：把网络状态变成可供选路比较的代价

**老师要求：**每条交换机链路的路由代价同时考虑当前负载和异常状态，使繁忙或受异常影响的链路更不容易被选中。

Task 2 的输出是“某个源异常”；Task 3 进一步把这个信息关联到它原来经过的有向链路，并结合实际负载计算分数。

### 代码怎样计算

`dynamic_cost_controller.py` 通过 OpenFlow 端口统计请求/回复读取计数。`link_costs.py` 的 `PortRates.sample()` 用字节增量计算速率。对 s2→s6，使用 s6 对应入口接口的接收字节，衡量实际到达对端的流量。

$$
R_{ij}=\frac{8\Delta B^{rx}_{j\leftarrow i}}{\Delta t},\qquad
U_{ij}=\operatorname{clip}\left(\frac{R_{ij}}{40\times10^6},0,1\right),\qquad
C_{ij}=C^0_{ij}+5U_{ij}+60A_{ij}.
$$

- `C0` 是教师拓扑中的基础代价。
- `U` 是利用率，参考容量为 40 Mbps。负载越高，代价越大。
- `A` 表示该方向是否处于检测异常引起的惩罚状态。异常在该方向生效时取 1，否则取 0。
- 5、60 是本项目选定的权重，不是教师指定的最优参数。

例如 s2→s6 的基础代价是 14。若端口测得恰好 10 Mbps，利用率为 0.25，正常代价为 15.25；再加入异常惩罚，变为 75.25。实际读数还会因协议头、采样窗口和排队变化而波动。

**代价是控制器用来比较路线的评分。增加 60 不会把实际延迟增加 60 ms，也不会把链路带宽改小。**

### 为什么封锁后还要观察恢复

入口已经丢包后，远端链路流量可能很快下降，但异常源可能仍在大量发送。因此 `sample_observed()` 继续观察入口 drop 计数：只要还在增加，就不能把源当成已经停止。

`LinkCosts.expire()` 在惩罚至少保持 8 秒、且入口丢弃计数连续 5 秒没有新活动后，解除链路惩罚。缺失或过期统计不作为“源已安静”的依据。**解除惩罚只恢复代价，不删除 Task 2 的源 IP 封锁。**

**验证：**看 s2→s6 从空闲约 14，变为正常负载下约 15.3，异常时约 75–77，源安静后回到正常负载代价；合法流也停止后才接近 14。单独的 Task 3 控制器仍保留静态转发规则，这一阶段验证代价算法，不拿它证明改道。

**汇报时可说：**“Task 3 将端口实测负载和异常标记转成有向链路权重，并用入口丢弃计数判断异常是否仍持续。这样 Task 4 可以比较当前路线，而不是一直使用固定基础代价。”

## Task 4：用动态代价改变合法流实际经过的路径

**老师要求：**先建立合法 h1→h6 流，再分别在三条指定链路引入异常；确认封锁、判断合法流是否改走更低代价路径，并记录路径、丢包、吞吐和恢复。

### 从“算出新路”到“交换机真的改道”

`rerouting_controller.py` 继承前面全部功能。`monitor()` 把最新链路代价写入网络图；`route()` 按这些权重求最短路线；`path_cost()` 将路线各边的代价相加。已封锁源不再为它更新转发路线。

B 场景中，合法原路是 s1→s2→s6，基础代价 19；替代路 s1→s2→s3→s6，基础代价 22。仅比较基础代价与异常惩罚时，s2→s6 被罚后，原路为 19+60=79，替代路仍为 22；实际决策还会加上各边实时负载项。

找到更便宜的路径后，控制器必须修改转发规则。例如 h1→h6 在 s2 的转发出口要由通往 s6 的 s2-eth6，改为通往 s3 的 s2-eth3；s3 也必须有继续发往 s6 的规则。只打印 ROUTE 或计算 Dijkstra 结果，数据包不会自行换路。

`send_rule()` 通过 OpenFlow FlowMod 安装这些规则。为减少更新过程中混用新旧路线，`commit()` 分阶段执行：

1. `prepare()` 先安装新路线下游规则，以内部 VLAN 标签区分路线版本。
2. `barriers()` 等待交换机确认已处理此前控制消息；这确认的是规则处理，不是端到端数据包交付。
3. `activate()` 再切换合法流入口，使新包带新版本标签并按新规则转发；目的交换机去掉标签，主机无需自己配置 VLAN。
4. 旧版本保留 5 秒，再由 `collect_old()` 按专用 cookie 删除。源封锁规则使用独立 cookie、较高优先级，不随旧路由清理被删除。

新路至少便宜 1 个代价单位，且距上次切换至少 3 秒才切换，以减少小幅负载波动造成的反复换路。异常惩罚撤销后，旧路再次更便宜时，使用同一更新过程切回。

### 三个场景为什么不一定都改道

| 场景 | 异常源/目的与目标链路 | h1→h6 原路线是否经过它 | 实际结果 |
|---|---|---|---|
| A | h2→h3，s2→s3 | 否 | 合法路线保持 s1→s2→s6 |
| B | h2→h6，s2→s6 | 是 | s1→s2→s6 → s1→s2→s3→s6 → s1→s2→s6 |
| C | h5→h6，s5→s6 | 否 | 合法路线保持 s1→s2→s6 |

A、C 保持原路是依据代价作出的合理结果，题目要求判断是否改道，不要求每组都强制换路。C 需明确披露：仅 h5→h6 测试对固定直接经过 s5→s6；它的无约束最短路实际是 s5→s3→s6。这项实验条件仍需向教师/TA 确认。

`student_task4_experiment.py` 使用当前 MiniEdit 网络安排约 60 秒实验：0–12 秒先发合法流，12–26 秒加入限时异常，之后观察恢复。它复用 `verify_rerouting.py` 采集接收数据、每秒流表、实际输出端口和包计数；三个场景独立启动，防止继承前一轮源封锁。

**验证：**结合 ROUTE 事件和实际流表、接口连接与递增包计数确认改道；用连续 ping 和接收端吞吐检查通信。测到的短暂丢包仍需如实记录，不能把版本更新机制说成无条件零丢包保证。

**汇报时可说：**“Task 4 把 Task 3 的代价用于最短路计算，并通过 OpenFlow 更新实际转发规则。B 的受影响链路正好位于合法原路上，因此发生改道及恢复；A、C 的合法原路未经过异常边，保持原路。改道过程中始终保留异常源的封锁。”

## Task 5：用数据评价上面的机制，不新增控制策略

**老师要求：**提供实际拓扑截图；评价异常前、中、后的行为；绘制归一化链路代价、丢包率、吞吐量随时间变化，并解释路径选择。

`analyze_task5.py` 的 `load_trial()` 读取已有实验日志；`plot_trials()` 绘制图表；`compare_task5_b.py` 冻结输入并比较 B 的三轮重复实验。它们不产生异常，也不向交换机下发规则。

| 输入数据 | 代码如何使用 | 对应老师要求 |
|---|---|---|
| `link-costs.jsonl` | 取目标链路 C(t)，除以其基础代价 C0 | normalized cost vs. time |
| `receiver.log` | 每秒 lost/total×100，读取接收端 Mbps | packet loss 与 throughput vs. time |
| `events.jsonl` 的冻结副本 | 标注检测、惩罚恢复、路线提交事件 | 解释何时发生变化 |
| `dataplane-samples.jsonl` | 提取实际路径、版本、输出端口和计数 | 解释数据实际经过的路线 |
| 原 MiniEdit 截图 | 放入报告 | 实际拓扑证据 |

归一化是 C/C0：A、B、C 分母分别是 10、14、20。它不是利用率，也不是除以曲线的最大值。吞吐必须取接收端，发送参数 10 Mbps 只代表提供负载。

保留每秒数据，特别是异常启动和改道附近的窗口。报告的稳定 before/during/after 窗口为 4–10、15–24、40–55 秒，但也同时报告完整 60 秒与一秒曲线，避免漏掉过渡时的丢包。

### 已有结果如何解释

| B 轮次 | 整轮 UDP 丢包 | 整轮丢包率 | 最低一秒接收吞吐 |
|---|---|---|---|
| B1 | 43/51024 | 0.0843% | 9.47 Mbps |
| B2 | 78/51024 | 0.1529% | 9.40 Mbps |
| B3 | 22/51024 | 0.0431% | 9.71 Mbps |

三轮 B 都实际改道并恢复，三轮整轮丢包率均值约 0.0934%。A、C 本次各一轮 UDP 未观察到丢包。B1 虽整轮丢包率低，但 12–13 秒窗口丢包约 5.07%；不能用全程平均掩盖短暂扰动。

五轮集成实验所有一秒接收窗口都有流量，稳定阶段接近 10 Mbps；这支持“经历短暂扰动后保持通信”，不支持“全程零丢包”。持续 ICMP 每轮为 121 发、120 收，不能与 UDP 丢包率混为一项。

B1 最初的 FAIL 来自检查器错误要求外部控制器的文本日志，不是把网络失败改写为成功；原始 FAIL 保留，完整原始流表和测量的离线核验另存为 PASS。

**汇报时可说：**“Task 5 将代价、实际路径、接收丢包和吞吐对齐到时间轴，解释检测、改道与恢复发生时的表现。三轮 B 都改道并恢复，稳定吞吐接近 10 Mbps，但存在短暂丢包，因此我们同时报告整轮和一秒窗口结果。”

## 老师追问时需要解释的三个点

**已经封锁，为什么还提高代价并改道？** 封锁针对源 IP，代价/改道针对合法流的路线选择，是两个机制。当前实现给异常路径保留一段时间的风险惩罚，即使入口封锁使实际负载下降，合法流也可暂时绕开。惩罚和保持时间是实现策略，不是物理链路仍必然拥塞的证明。没有“相同封锁但禁用改道”的对照实验，不能声称已量化改道相对仅封锁的独立收益。

**恢复是否等于把攻击源放回来？** 不等于。本实现恢复的是链路代价和合法路由，异常源 IP 仍被封锁，直到新一轮实验重启。已封锁源再次发包可增加 drop 计数并重新激活惩罚。

**这些结果证明到什么程度？** 证明固定六交换机拓扑和已测试负载下，检测、源封锁、代价变化、必要时改道和恢复可以协同工作。没有测试物理断链恢复、40 Mbps 饱和容量或最优参数，C 的固定测试对条件也需明确说明。
